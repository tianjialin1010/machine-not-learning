# 十日谈 · 哨兵：把判断从「过度自信」手里拿回来

**第三届 NVIDIA DGX Spark 黑客松 · Agent Skills 开发挑战赛参赛纪实**

**队伍：Machine not Learning｜作品：哨兵 EdgeSentinel · 工业报警智能处置中枢**

> 十日谈，十段历程。下面这十章按里程碑落笔——从拿到那台机器，到作品在它上面跑起来，记录的是我们真正走过的路，包括走错的那几段。

---

## 第 1 日（9/20）｜一台连不上的服务器

比赛第一天，我们拿到的是一台没有屏幕的机器。一台 NVIDIA DGX Spark，Ubuntu 24.04 + DGX OS，我们只有一个 SSH 端口、一行密码，以及一份写满注意事项的手册。三个人盯着终端敲下 ssh，等了四十五秒，屏幕上什么都没有。一开始我们怀疑自己的网络。后来才学会怎么给它"验尸"：先用真实协议探针去敲，发现端口 TCP 能连上、但服务端一个字节都不回；再用几个根本不可能有服务的随机端口去连——**居然也显示"连接成功"**。那一刻我们明白，所谓"端口通"是假象：网关在无脑放行握手，真正的判据是有没有协议数据回包。结论是节点当时没起来，不是我们的问题。同一天稍晚，它活了。**这台机器教我们的第一课，是"证据必须能证伪"。**这个习惯后来救了整个项目。

## 第 2 日（9/20 夜）｜摸清家底

节点通了之后我们没有急着写代码，而是先把家底量了一遍。

20 核 Arm 处理器、**121 GiB 可用统一内存**、931 GB NVMe、CUDA 13.0 完整 SDK（nvcc + cuBLAS + Nsight 双件套）、驱动 580.142。这台机器上还预装了一个 27B 的本地模型。我们直接测了它的推理：**13.0 tokens/s，100% 卸载到 GPU，功耗 44 W，温度 47 ℃**。按官方给出的内存带宽倒推，理论上限约 16.1 tokens/s——实测达成率 81%。不是慢，是满血。同一天我们撞上了一堵墙：**节点访问国际源几乎全断**。PyPI、PyTorch 官方源、NVIDIA NGC、Docker Hub 全部超时。手册推荐"优先用 NGC 容器省掉环境折腾"，在我们的机器上完全走不通。这个信息后来被我们写进了队内文档，也让我们从一开始就决定：**所有依赖都要能离线落地。**

## 第 3 日（9/21 上午）｜一张截图引发的转向

选题那天，队友在群里丢了一张截图。截图里是一个叫 Jev 的模型——它不写一个字，只对预先声明的问题返回三种类型化决策：**是不是（概率）、选哪个（分布）、打几分（打分）**。它的训练目标不是"让人喜欢"，而是"报的概率要诚实"：说八成把握的事，长期看就得有八成对。我们盯着这张截图讨论了很久，最后想通了一件事：**工业现场最缺的不是会说话的模型，而是敢把话说死的判断。**一台产线上的设备，一天可能报上千条报警，其中绝大多数是误报或低危。让一个聊天模型去"判断"，它会写一段很流畅的分析，然后你既不知道它多大把握，也不敢让它自动开工单。于是我们定下了方向：**不做聊天机器人，做一个决策层。**不生成文字，只输出概率；决定权交给确定性代码，不交给模型。

## 第 4 日（9/21 中午）｜第一个决策头跑起来了

方向定了，第一件事是找数据。工业报警分诊需要"传感器数值 → 故障判定"的带标签数据。我们盯上了公开的 AI4I 2020 预测性维护数据集（一万条机加工设备记录、五类故障标签）。节点连不上数据源，就从本机下载再传上去——**522 KB 的压缩包，走 scp 花了不到一秒，比在节点上等 10 KB/s 的国际带宽快两个数量级。**

当天下午，第一个决策头原型跑起来了：一个吃 9 维结构化特征的小网络，输出三个决策——是否故障、故障类型、维护优先级。它的单条推理耗时是 **0.097 毫秒**。而我们前一天测的生成式方案，出同样三个决策要 **83.7 秒**。差了将近六个数量级。那天晚上我们没敢相信这个数字，第二天专门回去复现了一遍，确认无误。

## 第 5 日（9/21 下午）｜差点被自己的兜底值骗了

为了证明"校准"这件事有价值，我们设计了一个对照实验：让那个 27B 模型对 40 个样本自己报故障概率，测它的置信度和实际准确率的差距。第一轮结果出来，40 个样本**全部返回 0.5**，ECE 等于 0。

"完美校准"——这个结果太漂亮了，漂亮到不像真的。我们起了疑心，去翻模型的原始输出，发现它返回的是**空字符串**。0.5 是我们自己脚本里的兜底值。根因是：这个 27B 是带思考链的模型，我们给的输出长度上限只有 60 个 token，全部被思考过程吃光了，答案一个字都没生成。改成关闭思考链重跑之后，真相是：

| | 27B 自报 | 我们的决策头 |
|---|---|---|
| 平均置信度 | **0.912** | （不适用） |
| 实际准确率 | **0.475** | **0.829** |
| ECE（校准误差） | 0.4375 | 0.1675 |
| Brier 分数 | 0.4325 | 0.1183 |

**模型嘴上说"我有 91% 把握"，实际只对 47.5%——在这个任务上几乎等于抛硬币，却自信得不行。**

如果那晚我们信了"ECE = 0"的假结果，后面所有论证都会建在沙子上。这一天之后，我们给队里加了一条规矩：**任何"太漂亮"的数字，先回去看原始输出。**

## 第 6 日（9/21 深夜）｜给概率"上秤"

拿到 0.475 这个数之后，逻辑就通了：**问题不在模型不够强，而在它报的概率不可信。**所以我们给决策头加了校准：在标定集上拟合温度参数，把"过度自信"和"过度谦虚"都拉回到诚实的位置。但校准这东西有个反直觉的性质。我们的决策头在**自然分布**下（故障率 3.1%）校准误差只有 0.0066，看起来完美；一旦换成**均衡分布**（正负各半），误差立刻涨到 0.1675——**因为校准是相对于部署分布成立的，分布一变就失效。**我们给它加了先验校正，把误差从 0.1675 压到 **0.0500，改善 71%**；又验证了两个稳健性条件：**先验猜错也比不校正强**，以及**在先验未知时可以用无标签方法盲估**。这一晚我们给项目找到了核心命题：**判断和表达必须分离，概率必须校准。**一句"我有八成把握"，只有在它真的有八成对的时候，代码才敢拿它做自动化的判据。

## 第 7 日（9/22）｜把决策头搬上 GPU

校准解决了"准不准"，接下来解决"快不快"和"稳不稳"。我们把决策头从 CPU 上的 sklearn 版移植成 PyTorch 模型跑在 GB10 上。预期是"批量快、单条慢"，结果实测把我们的预期推翻了：**GB10 是统一内存架构，没有独立显存搬运开销，连单条都比 CPU 快**——0.0339 毫秒对 0.097 毫秒，快 2.9 倍。批量峰值跑到 3 亿条/秒。同一天我们把它做成了服务，并修掉了两个真正危险的架构缺陷：

**缺陷一：三个决策头会自相矛盾。**因为它们是独立训练的，出现了"Noul 判 99.3% 是故障、Choice 却判 64% 无故障"这种荒诞输出。我们加了一层一致性绑定，让两个决策必须自洽。

**缺陷二：路由判据用错了。**我们原本用"故障概率 ≥ 阈值"来决定自动派单，结果在一千条样本里只触发了十次。正确的判据是**置信度 = max(p, 1−p)**——不确定就转人工，无论是"确信有故障"还是"确信没事"。改完之后，自动化率一下从 1% 跳到 88%。这两个缺陷都不报错、不崩溃，只是安静地把系统做废。**它们让我们意识到：这个系统里最危险的东西，是"看起来在工作"。**

## 第 8 日（9/22 夜）｜一场对决实验

到这里，我们有了一个大胆的说法："通用大模型在这个任务上不如我们的垂类决策头。"

为了不让这句话停留在观点层面，我们做了一场正经的对决实验：140 条均衡样本、三个决策任务同批对比、两个不同规模的模型（8B 与 27B）、三档信息量（裸数值 / 加领域知识 / 加示例），确保不是"提示词没写好"。结果比我们预想的更干脆：

- **裸数值喂给 27B，它等于瞎猜**：精确率、召回、F1 全是 0，MCC 是 **−0.085**（比随机还差）——它把 140 条全部判成了正常，一个故障都没抓到。
- **知识和示例能救，但有天花板**：平衡准确率从 0.493 提到 0.643，还是够不着决策头的 **0.829**。
- **小模型走向另一个极端**：8B 的召回率是 1.000、精确率只有 0.52——几乎把所有设备都判成故障，典型的"狼来了"。
- **开思考链在实时场景直接出局**：27B 开思考，20 条样本**全部超过 90 秒未完成**，0 条可用。速度差 **11.6 万倍**。但这场实验最重要的产出不是"我们赢了"，而是边界：**通用大模型强在非结构化文本（维修工单、手册、报告生成）和长尾罕见故障，这些恰是垂类决策头做不了的。** 所以正确的架构不是二选一，而是分层——高频、结构化、要求确定性的判断交给决策头；罕见、模糊、需要语言理解的才升级上去。

## 第 9 日（9/23–9/27）｜两条线合并：六项缺陷与两处「静默出错」我们的队伍其实是两条线：**我负责跑实测、出评测数据；队友负责把框架一层层迭代。**这个分工在第九日迎来了最有价值的一次碰撞。我把测试反馈整理成清单交给队友——他据此把决策框架从 0.1.1 一路迭代到 0.1.4；而我在真机上验证新版本时，又挖出了六项缺陷。其中前四项是"跑不起来"（配置与解析器对不上、概率和不为一、取值越界、输出被截断），真机实测原版 **3 次全失败**，修复后 **3 次全成功**。

**真正危险的是后两项——它们都"跑起来了，但保护失效"：**

**其一是"好心办坏事"**：系统里有一道安全闸——最高级别报警必须转人工。但一打开校准功能，等级数值被改写成了文字标签，而判断逻辑看的是"这是不是数字"，类型一变整道闸就被静默跳过。结果：**最紧急的报警，被系统当成普通消息自动回掉了，不报错、不提示。**

**其二是"越诚实越不可用"**：配置里有一栏"我们哪些类别样本不足"，队友如实填了。但框架的逻辑是"只要这栏不是空的，所有请求一律转人工"——不管来的是健康设备还是故障设备。**诚实标注反而让系统整体停摆。**这两个缺陷让我印象极深。它们不崩溃、不报警，只是在安静地做错事。我们花了两天把它们定位、复现、修复，并把结论写成正式文档交给队友。而最让我们受用的一次"打击"，发生在同一周：**队友读完我们的多工业数据集评测报告后，逐条列了七条方法论质疑，其中一条直接指出我们原文有事实错误**（我们写"所有数据集的校准误差都恶化了"，但有一个数据集的误差其实是全部里最低的），另一条指出我们用了随机行划分处理**时序数据**，存在泄漏风险。我们照单全收，并把它们写进了后续的修正计划。**被队友挑错，比在评审面前被挑错便宜太多了。**

## 第 10 日（9/28–9/29）｜正式接入，与一条悬崖

最后两天做的是"合龙"：把我们的决策头正式接进队友的决策框架，让两条线变成一个系统。接法的原则是**不改框架一行代码**——框架本来就留了一个标准接口，我们只填那个口子。三层路由也随之成型：**决策头（亚毫秒）→ 低置信升级到生成式 → 兜底与弃权**。同时我们把云端升级层接到了赛事赞助方 StepFun 的官方接口上（JSON Schema 结构化输出 + 有限退避重试），密钥一配即可启用——本地决策头负责高频判断，云端模型负责长尾与语言理解，这也让 DGX Spark 的本地算力和云端能力各归其位。上线后，我们在真实留出集上跑了一次端到端评测（1000 条、走完整链路）：

| 指标 | 实测 |
|---|---|
| 自动化率 | **88.3%** |
| 自动部分准确率 | **100%** |
| **故障漏放率** | **0%** |
| 引擎延迟 | p50 0.536 毫秒 |

然后是这次比赛里我们认为**最有说服力的一张表**——调一个阈值，看会发生什么：

| 阈值 | 自动化率 | 故障漏放率 |
|---|---|---|
| 2.5（我们采用的） | 88.3% | **0%** |
| 3.0 | 90.5% | 0% |
| 3.05 | **94.1%** | **10.0%** |

**拐点是一个悬崖**：阈值再放宽一档，自动化率只多 1.4 个百分点，**故障漏放却从 0% 跳到 10%**（3 条真实故障被当成正常归档）。这张表解释了我们为什么坚持做校准、坚持留出集、坚持把每个数字连同它的口径一起写下来——**因为"多赚一点自动化、赔掉安全底线"的那个区间，凭感觉是发现不了的。**

最后一天，队友把框架升级到了 0.1.5（代码量增加 47%、测试从 35 项增至 70 项）。我们重新跑了一遍对比：**主指标持平，我们之前报的三项框架问题全部被修掉**——包括那两处"静默出错"。

## 尾声｜我们真正学到的三件事

十日谈讲了十天，其实只讲了三件事。

**第一，诚实是工程能力，不是态度。**我们报告里最显眼的位置摆的不是 97.8% 的准确率，而是平衡准确率 0.829 和 MCC 0.665——因为前者的高是被 96.6% 的正常样本撑起来的。我们还在同一页写下了"严重度标签是我们自己用规则派生的，这些数字不能外推"。**主动说出局限，比被问出来便宜。**

**第二，口径比数字重要。**同一套模型，"批量摊销的推理耗时"和"单请求端到端延迟"能差几个数量级；"自然分布"和"均衡分布"下的校准误差完全不同。我们吃过口径混用的亏，也因此统一了所有对外数字的测量方式，并把测量脚本一并交付。

**第三，最强的技术不是模型，是知道自己什么时候不知道。**这十天里我们做的大部分工作，其实不是让机器判得更准，而是让它**知道自己有多准**——然后据此决定：这一条可以自动处置，那一条必须交给人类。这大概就是"哨兵"这个名字的由来。
